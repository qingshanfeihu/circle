Circle TUI 交互契约草案

回答一个问题：为什么单看每一屏都还行，合在一起就乱。答案是 Circle 有渲染契约、没有交互契约。这份草案把两者补成一套，供逐项裁决。

2026-09-29 · 依据：circle main（d3c8b94）全量盘点 · InfoTest 07 章 §11.11/11.16/11.23/11.25 · Claude Code / Codex / Gemini CLI / opencode / Crush / pi / Aider / Kimi 公开源码与文档

0结论

Circle 的界面是两条血统叠出来的。渲染层（块间节奏、类型底色、字形分职、单行页脚、彩虹框）从 InfoTest 移植，有文档、有守门测试。交互层（审批、提问、/approvals、计划面板、plan mode、yolo）是对标 Pi/OpenCode 另起的，每个功能自己决定放在哪、怎么抢焦点、用什么颜色、说哪种语言。渲染契约管「一行长什么样」，不管「现在该看哪、该按什么」。缺的正是后者。

补法不是再画一版好看的，是先立四条交互规则，再让所有面板服从它：

  1. 一个焦点。屏幕上任何时候只有一个带框的东西，它就是键盘焦点。谁要用户，谁接管这个框。
  2. 一种问法。审批、提问、始终允许的二次确认、/approvals 页，是同一种「问答卡」的四个实例，不是四个组件。
  3. 一眼看出轮到谁。四档注意力：静默、进行中、等你、出错。每档一种视觉信号，不叠加。
  4. 一种语言面。屏幕句子是中文；命令名、工具名、按键名、计量单位是英文闭集。中英之间空一格。

推进用 InfoTest 已经验证过的方法：写 A/B 方案 demo 走真实 ink 管线出 ANSI，终端里并排比，逐项裁决，落成 docs/tui_contract.md 和守门测试。

2产品与用户

README 的定位一句话：终端里的 AI coding agent，接自己的模型网关，在项目目录里读改跑。用户画像从仓库和实验室用法能推出来：

  • 中文工程师，接国产或私有网关（qwen3.8-flash、glm 等），模型不一定会写粗体标题、思考流是整段 prose，所以界面不能依赖模型自产的摘要。
  • 会跑长任务（compile-excel 一批 5 案跑 40 分钟以上，几十次工具调用，多个子代理），大部分时间是在看，不是在打字。
  • 会被反复打断：逐项审批一场会话几十次，Claude Code 用户也抱怨 30 到 50 次。审批的形态决定疲劳程度。
  • 在 Otty / tmux 里用，浅色和深色主题都有（Ghostty Catppuccin Latte 实测浅底），颜色必须从终端派生。

用户实际经历的六个时刻

把一场会话按「用户此刻在干什么」切开，界面要服务的就是这六个时刻，每个时刻只有一个主问题：

时刻用户的问题屏幕必须回答用户会按
输入我能打字吗，现在是什么模式光标在框里，模式标签（若非默认）打字、/ 命令、↑ 历史
观察它在干什么，卡了没有，花了多少忙碌词加耗时加 token，工具行逐条落下，中断键esc 中断、enter 插话、ctrl+o/t 展开
被问它要我干什么，选哪个，选了有什么后果问题、对象、选项、每个选项的作用范围、默认项数字或助记键、方向键、enter、esc
核对它改了什么，对不对diff、结果摘要、失败原因ctrl+o 展开、滚动、拖选复制
跟进计划做到第几步了，下一步是什么进度、当前项、下一项ctrl+p 展开
出错或结束成了没有，没成是为什么，花了多少终帧一行，Cooked 一行继续输入或 /undo

现状的问题是「被问」这个时刻没有被当成独立时刻设计：审批面板长在输入框上方、框还在转、焦点样式和提问面板不同，用户要靠读文字才知道轮到自己了。

4分区规则

这一节是全文的核心，其余章节都是它的下游。设计美学在终端里不是字形和颜色，是什么信息、什么条件下、进哪个区、待多久、谁把它撤掉。六个区各管一类信息，一条信息只属一个区。

4.3 由分区推出的六条规则

R1 唯一焦点框对话框不是第二个框，是同一个框换内容。屏幕上任何时候只有一个带边框的东西。
今天审批面板叠在框上方，两个框并列，用户要读文字才知道键盘归谁。
R2 彩虹说轮到谁流动是模型的回合，黄色静止是你的回合，淡色是空闲。等你时框停转、忙碌词撤下。
今天等你和进行中视觉相同。
R3 阻塞的问题一种卡审批、提问、机密、trust 共用一个组件：标题行带青灯，正文，空行，竖排选项。键一列（数字，dim）、标签一列，当前项整行 sel_bg。助记键可按不显示。esc 永远是最保守的答案，不另写提示。
R4 不阻塞的列表一种弹窗/models、/resume、补全、/approvals、? 共用一个组件：框上方 panel 底列表，框里照常打字过滤。
R5 状态词只有两个，各占一角忙碌词左上、模式词右下，都是单词：read-only（原 plan mode，改名避免和计划块撞词）、auto（原 yolo）；默认的逐项审批什么都不显示。边框上不再放别的字；标题是内容，写在框里。
R6 通知按「以后还要看吗」分要看的进转录，永久淡色；不要看的走一闪，页脚右 1.2 秒；正在成立的走常驻，撤了就没。代码里两个 toast 改名 notice 和 flash。

4.4 宽度、换行与对齐

W1 宽度每帧读真实列数，两档≥ 100：标准。< 100：收缩，页眉只留身份，子代理条先缩「在做什么」列。计划块和焦点框始终全宽。
W2 正文换行，状态行截断你的话、模型的话、问题、命令、选项、通知是正文：换行，续行对齐所在行的文字列，绝不截断。审批卡里的命令尤其不能截，用户要读完才能批。工具行、结果摘要、计划行、子代理行、页眉、页脚、忙碌词是状态行：单行，超宽按优先级截断。
W3 截断优先级先丢右侧整个组件（页眉提示、页脚一闪、计划行的 next），再截可变段（参数尾截、「在做什么」尾截、路径从左截保留尾巴 …/circle），灯、名字、数字、按钮永不截。
A1 列按显示宽度算中文两格，用 string_width，不数字符。
A2 左网格页边距 1；标记列 1、文字列 3；子行连接符 ⎿ 列 3、子文字列 5。框内整体加 1。卡片的键、输入行的 ›、转录的灯同一列。
A3 右网格所有靠右的东西统一止于倒数第 2 列：页眉提示、页脚一闪、页面顶栏按钮、模式词、子代理行的计量。
A4 列表对齐名字列按本屏最长者定宽；数字列右对齐；计划编号右对齐到 2 格；双列清单列宽由内容算，不写死。
A5 矩形铺底色或在框内的行补空格到整宽，块才是矩形；无底色的行到内容为止。

8推进方法

沿用 InfoTest 2026-09-24 那轮的方法，它已经在这套 ink 管线上跑通过一次：

  1. 先裁决规则，再画。本文 R1 到 R6、D1 到 D6 逐条过，每条要么采纳、要么改写、要么否掉并写理由。规则定了，方案数量会自然收敛。
  2. 写方案 demo，走真实管线。仿 docs/demo/tui_schemes_20260924/demo.py，在 circle 里建 scripts/tui_schemes_demo.py：同一份 mock 会话（含审批、提问、计划、子代理、中止五个场景），A 方案 = 现状，B 方案 = 本契约，用 theme.palette() 和 Output.write 出 ANSI。不写 HTML，终端里看到的才算数。
  3. Otty 并排比。两个 pane 各跑一个方案，同一宽度，浅色和深色主题各看一遍。逐场景裁决，记录在 demo 的 index 页。
  4. 落契约。裁决结果写成 docs/tui_contract.md，格式沿用 07 章 §11.25 的编号条款：每条一句规则、一句为什么、一个守门测试名。
  5. 守门先行。先把状态矩阵写成 tests/test_interaction_contract.py（每行一个用例：这个状态下按这个键，焦点框是什么、字符去了哪），再改实现。字形和语言面扩 test_render_colors.py 的扫描面和词表。
  6. 按差距清单分批。第一批只做 R1 R2 R3（审批接管焦点框），这是用户抱怨的源头，做完就能在真机上验证方向对不对。R4 到 R6、D 系列各成一批。

第一批的验收标准只有一句：模型发起审批时，用户不读任何文字，靠框的颜色和停转就知道轮到自己，按一个数字键就能答。
